# GENESIS

> **إطار محلي قابل لإعادة الإنتاج لتجارب الذكاء الاصطناعي متعددة الوكلاء والقابلة للقياس.**

GENESIS مشروع مفتوح المصدر يدرس ما إذا كان التعاون المنظم بين أدوار ذكاء اصطناعي متخصصة يمكن أن ينتج أساليب أفضل لحل المشكلات، مع تقييم مستقل وسجل كامل للأدلة.

المشروع لا يدّعي أنه AGI، ولا يدّعي الوعي، ولا يمنح الوكلاء صلاحيات غير محدودة. السؤال الأول للمشروع أصغر وقابل للاختبار:

> **هل يستطيع نظام منظم أن يقترح حلًا، ويبنيه، ويختبره، وينتقده، ويحفظ نتائجه، ثم يقارن بين الاستراتيجيات مع توضيح سبب قبول إحداها؟**

![معمارية GENESIS](docs/images/architecture.png)

## لماذا GENESIS؟

كثير من عروض الأنظمة متعددة الوكلاء تكتفي بإظهار نماذج تتحدث مع بعضها ثم تعتبر المحادثة تقدمًا. GENESIS يستخدم معيارًا أكثر صرامة. المحادثة طبقة اقتراح فقط، أما الوحدة الأساسية فهي **التجربة** التي تحتوي على المهمة والاستراتيجية والمخرجات والتنفيذ والتقييم والنقد والقرار.

لذلك فإن كل ادعاء بتحسن يعامل كادعاء علمي. يجب مقارنته بخط أساس ثابت، وقياسه في نفس الظروف، وتقييمه بواسطة مقيّم مستقل، وحفظه مع حالات الفشل واستخدام الموارد.

## كيف يعمل GENESIS؟

![دورة عمل GENESIS](docs/images/workflow.png)

التسلسل هو:

1. `Task` يحدد المشكلة ونسخة الـ Benchmark.
2. `Strategy` يحدد طريقة العمل.
3. `Researcher` ينتج فرضية وخطة منظمة.
4. `Builder` ينتج Artifact.
5. المشغل المقيد ينفذ الـ Artifact في مجلد مؤقت.
6. المقيّم المستقل يشغل حالات الاختبار خارج تحكم الـ Builder.
7. `Critic` يحلل حالات الفشل ولا يقرر النتيجة بدلًا من المقيّم.
8. SQLite يحفظ التجربة والأحداث والقياسات.
9. GENESIS يسجل قرارًا نهائيًا مثل `verified` أو `rejected` أو `failed`.

## تشغيل المشروع خطوة بخطوة

```bash
git clone https://github.com/osamahdesk/GENESIS.git
cd GENESIS
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

تهيئة مساحة العمل:

```bash
genesis init
```

تشغيل التجربة الأولى:

```bash
genesis run
```

عرض التجارب المخزنة:

```bash
genesis status
```

فتح الواجهة التعليمية:

```bash
genesis dashboard
```

ثم افتح:

```text
http://127.0.0.1:8765
```

## الواجهة التعليمية

الواجهة مصممة لتكون بسيطة وقريبة من تجربة GitHub:

- شريط جانبي يوضح أقسام المشروع.
- بطاقة حالة تعرض آخر تجربة.
- بطاقة نتيجة تعرض النسبة وعدد الاختبارات.
- مسار بصري يوضح انتقال المهمة من Task إلى Verified Result.
- فقاعات Hint تشرح وظيفة العناصر عند المرور عليها أو الضغط عليها.
- قسم Quick Start يوضح الخطوة التالية.
- قسم صلاحيات يوضح ما هو مسموح وما هو مغلق.
- أزرار ON/OFF لتفعيل Transformers وPyTorch وHugging Face وAI Builder وModel Training.
- كل زر يغيّر سياسة التجربة فقط؛ لا يثبت حزمة ولا يشغّل كودًا تلقائيًا.
- التصميم يعمل على شاشة الكمبيوتر والهاتف.

الواجهة لا تتطلب خدمة خارجية، وتقرأ من نفس سجل SQLite الذي يستخدمه CLI.

## الصلاحيات والأمان

لا يمنح GENESIS نفسه صلاحية مباشرة لجهاز المستخدم عند الدخول. الوصول المباشر التلقائي سيكون خطرًا وغير متوافق مع مبدأ الأمان. بدلًا من ذلك، توجد طبقة صلاحيات صريحة:

```text
صلاحيات المستخدم
      ↓ موافقة صريحة
سياسة GENESIS
      ↓ أقل صلاحية مطلوبة
الأداة أو التجربة
```

الإعداد الافتراضي:

```text
Network: OFF
Host filesystem: DENIED
Shell: DENIED
Private data: DENIED
External actions: DENIED
```

إذا احتاجت تجربة إلى صلاحية إضافية، يجب أن تكون محددة وواضحة وقابلة للمراجعة. مثال آمن هو السماح بالكتابة داخل مجلد المشروع فقط، وليس إعطاء البرنامج كامل القرص.

يمكن للمستخدم مراجعة السياسة من خلال:

```bash
genesis permissions
```

كما يمكن تغيير القدرات من زرها داخل الواجهة. عند تفعيل `AI Builder` يستطيع GENESIS إنشاء Proposal لمشروع نموذج داخل Sandbox. الـ Proposal يحتوي على اسم المشروع والمكتبات المطلوبة وملف README، لكنه لا يشغّل الكود ولا يثبت المكتبات ولا يصل إلى جهاز المستخدم مباشرة. بعد ذلك يجب أن يمر المشروع بمرحلة مراجعة وتقييم مستقلة.

ومن ثم منح صلاحية محددة فقط عندما يفهم أثرها. لا يتم تمرير كلمات المرور أو الأسرار إلى الوكلاء تلقائيًا.

## المدخلات والمخرجات

المثال الحالي هو `python-sum-squares-v1`.

المدخل:

```json
7
```

المخرج المتوقع:

```json
140
```

نتيجة التجربة:

![نتيجة التجربة الأولى](docs/images/result.png)

```json
{
  "status": "verified",
  "score": 1.0,
  "passed": 7,
  "total": 7,
  "critique": {
    "failure_count": 0,
    "summary": "No failures detected."
  }
}
```

هذه النتيجة تثبت نجاح خط الأساس على Benchmark المثال فقط. لا تعني أن النظام أصبح ذكيًا بشكل عام، ولا تعني أن النموذج طور نفسه.

## هندسة السرعة

السرعة في GENESIS خاصية مقاسة وليست ادعاءً ثابتًا. أضفنا ثلاث طبقات: وضعًا معزولًا يشغل كل حالة في عملية مستقلة، ووضع Batch يشغل مجموعة الحالات داخل عامل معزول واحد مع Namespace جديد لكل حالة، وCache يعيد النتيجة فقط عندما يتطابق Hash الكود والحالات وطريقة التشغيل.

القياس الفعلي لنفس Benchmark المكون من سبع حالات:

| المسار | الزمن | النتيجة |
|---|---:|---|
| التقييم المعزول لكل حالة | 0.327261 ثانية | 7/7، النتيجة 1.0 |
| التقييم المجمع Batch | 0.047891 ثانية | 7/7، النتيجة 1.0 |
| إعادة التقييم من Cache | 0.000051 ثانية | Cache hit، النتيجة 1.0 |

هذا يعادل **6.83×** في التقييم المجمع، وحوالي **939×** عند إعادة نفس التقييم من Cache في الذاكرة. هذه أرقام Benchmark محدد وليست وعدًا بأن كل نموذج أو مهمة أو جهاز سيحصل على نفس النسبة.

لتكرار القياس:

```bash
python tools/benchmark_speed.py
python tools/benchmark_cli_cache.py
```

وضع Batch أسرع، لكنه مخصص للـ Artifacts التي نتحكم بها. عند التعامل مع كود عدائي أو غير موثوق يمكن استخدام الوضع المعزول عبر `IndependentEvaluator(accelerated=False)`.

## نموذج Hugging Face المضمن

تتضمن المرحلة الثانية نموذجًا صغيرًا هو `sshleifer/tiny-gpt2` من Hugging Face. النموذج موجود داخل:

```text
models/sshleifer-tiny-gpt2/
```

ويوجد معه ملف `SHA256SUMS` للتحقق من الملفات.

لتشغيله:

```bash
pip install -e ".[hf]"
python examples/first_experiment/huggingface_local.py
```

النموذج صغير ومخصص لإثبات التكامل المحلي، وليس نموذجًا إنتاجيًا عالي الجودة. المسار الافتراضي لا يزال يعمل بدون تثبيت PyTorch أو Transformers.

## مركز اختيار النموذج المعلم

لا يحتاج المستخدم إلى معرفة تفاصيل النماذج. من داخل Dashboard يمكنه اختيار نموذج مقترح حسب ذاكرة الجهاز، أو كتابة `owner/model`، أو لصق رابط Hugging Face، أو إدخال مسار مجلد نموذج محلي. يحفظ GENESIS الاختيار كـ `teacher.json` ويستخدمه كمرجع للتجارب القادمة.

يوجد أيضًا بحث اختياري في Hub API العام. يظهر البحث عند تفعيل قدرة Hugging Face والسماح بشبكة قراءة فقط. يعرض اسم النموذج والتنزيلات والإعجابات، ثم يمكن الضغط على `Use` لتعيينه كـ Teacher.

المعلم لا ينسخ نفسه مباشرة ولا يستبدل النظام. دوره إنتاج اقتراحات ومرشحين داخل Sandbox، ثم تمريرها إلى المراجعة والتقييم والبوابة الانحدارية.

## المرحلة الثانية

تركز المرحلة الثانية على إدخال نموذج حقيقي، ثم بناء مقارنة علمية بين:

```text
Mock baseline
      ↓
Local Hugging Face model
      ↓
Repeated trials
      ↓
Validation and hidden evaluation
      ↓
Cost and latency metrics
      ↓
Frozen baseline
      ↓
Strategy evolution
```

لا يتم اعتبار النموذج الحقيقي أفضل لمجرد أنه موجود. يجب أن يمر بنفس التقييم والميزانية والاختبارات.
