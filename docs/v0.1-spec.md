# GENESIS v0.1 Approved Specification

## Scope

v0.1 is a local-first, CLI-based experiment runner for small Python problem-solving tasks. It is deliberately smaller than the long-term GENESIS vision.

The release must provide one complete path from task definition to independently recorded evaluation. It does not need dynamic roles, web browsing, a dashboard, or automatic permanent self-modification.

## Required components

### Task and benchmark

A task has an identifier, statement, input/output contract, visible development tests, validation tests, and a hidden evaluation set. The builder may receive the task statement and permitted development information, but the hidden evaluator remains outside the writable execution environment.

### Provider

The provider interface isolates model-specific behavior. The interface must expose model identity, request metadata, structured output handling, timeout behavior, and failure classification. API keys are loaded from the environment and never stored in experiment artifacts.

### Agents

The first implementation uses three logical roles:

- **Researcher:** produces a structured hypothesis and implementation plan.
- **Builder:** produces a candidate artifact under an explicit artifact schema.
- **Critic:** analyzes measured failures and proposes a repair or rejection explanation.

The evaluator, not the Critic, decides whether the artifact passed.

### Runner

The runner executes generated artifacts with explicit limits for time, memory where supported, disk, retries, subprocess behavior, and network access. The project must document that local restrictions reduce risk but are not a perfect security guarantee.

### Evaluator

The evaluator is independent from the builder workspace. It returns structured metrics, test-level outcomes, error classification, runtime, and resource data. The evaluator must be deterministic where possible and versioned as part of the benchmark.

### Experiment store

Each experiment stores its hypothesis, strategy, parent, model configuration, prompt versions, benchmark hash, artifacts, logs, metrics, status history, and final decision. A completed experiment must be exportable as a reproducibility bundle.

## Experiment lifecycle

```text
CREATED
  → RESEARCHING
  → BUILDING
  → EXECUTING
  → EVALUATING
  → CRITIQUING
  → STORED
  → VERIFIED | REJECTED | FAILED | BUDGET_EXCEEDED
```

A retry creates a new attempt record linked to the original experiment. It must not overwrite the first result.

## v0.1 acceptance criteria

- A clean environment can install the package from the repository.
- One command can run a complete example experiment.
- The experiment record survives a process restart.
- The evaluator is not writable by the generated artifact.
- Visible and hidden evaluation are separated.
- Every run records model, prompt, benchmark, configuration, dependency, and environment metadata.
- At least three independent runs are supported for a strategy comparison.
- The output reports correctness, latency, resource usage, model calls, tokens when available, and estimated cost when available.
- Failed, timed-out, and budget-exceeded experiments are preserved rather than silently discarded.
- The project can operate in offline mock-provider mode for tests.

## Explicitly deferred

The following are not part of v0.1: dynamic role creation, generated tools, browser automation, external actions, distributed orchestration, vector databases, fine-tuning, model training, and automatic deployment.
